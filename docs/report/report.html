Architecture

The app is deliberately small. The project is the delivery system around it: how one commit travels from the laptop to a monitored Kubernetes cluster, safely and automatically.

A change: from git push to production

01
git pusha commit to main on GitHub
02
Tests firstpytest and the Vite build; a failure stops everything
03
ScanBandit, Semgrep, pip-audit, npm audit, Trivy fs, Gitleaks
04
Build + image scanboth images built once; Trivy scans the exact files
08
KubernetesIngress, 2 frontend pods, backend HPA 2–4, PostgreSQL
07
Argo CDwatches main, syncs the cluster to Git
06
Push + promoteGHCR tag = commit SHA; helm test; tag committed to gitops/
05
Security gatereads all 8 reports; any HIGH / CRITICAL stops the run

CI never touches the cluster and no cloud or cluster credentials are stored in GitHub. Rolling back is git revert.

A request, and who watches it

Ingress (ingress-nginx)/ → frontend: nginx serving the React build, 2 pods. /api → backend: FastAPI, autoscaled 2–4 pods
PostgreSQL 17StatefulSet with a persistent volume (gp3 EBS on AWS); password from a Secret that is never in Git
Prometheus + GrafanaServiceMonitor scrapes /metrics every 15 s; 4 alert rules; 12-panel dashboard

It ran in three places: on AWS EKS in Sydney (built by Terraform, destroyed after testing), on a local kind cluster deployed by Argo CD from GitHub (the live demo and the troubleshooting challenge, at no cost), and with Docker Compose for local development.

Cost: $0 billed

GitHub, Actions, GHCR and the local cluster are free. The AWS session (EKS, NAT gateway, one node, about 1 h 20 min) used about $0.40 of Free Tier credits on the AWS Free plan. Everything was destroyed afterwards, and the Terraform user and its access key were deleted (docs/TEARDOWN.md).

No secrets anywhere

Gitleaks scans the whole Git history on every run. The database password lives in a git-ignored .env and in a Kubernetes Secret; Grafana's is random; the pipeline uses only GitHub's own short-lived token.

M6

DevSecOps

5 pts

What Trivy scanned and what it means

Trivy scanned the operating-system packages and the Python and Node dependencies inside both images, using the exact files the pipeline pushes, and found 0 HIGH or CRITICAL. That is deliberate: the upstream nginx base image has 43 fixable HIGH/CRITICAL CVEs, for example CVE-2026-33630, a use-after-free / double-free in the c-ares DNS library (1.34.6, fixed in 1.34.8). The frontend Dockerfile runs apk upgrade and removes curl to patch them, and the gate fails the pipeline if one comes back. The scanners are pinned and verified with SHA-256 checksums.

Troubleshooting challenge

Every fault arrived the way real outages do: as a commit. troubleshooting/inject.sh pushed a small, harmless-looking change to the GitOps values file and Argo CD deployed it. Each was identified, investigated through logs and resources, root-caused, fixed with git revert and verified. Full write-up: troubleshooting/README.md.

The method, the same every time

Symptom (curl, argocd app get) → resources (kubectl get, describe, events) → logs (--previous, the ingress controller) → the wrong object → the commit (git log) → git revert → check the symptom again.

Also documented: six real problems

AWS refusing aws login; the one-region account policy; the node group's missing service-linked role; the EBS driver without credentials (fixed with Pod Identity); the PostgreSQL image versus Pod Security; Argo CD's brief "Degraded" after a rollout.

Lessons learned

  1. Healthy isn't working. The Ingress typo passed every probe and Argo CD check while every user got a 404. Something has to test the public URL.
  2. GitOps makes every change reviewable and reversible. Faults, fixes and deployments are all commits; a rollback is git revert.
  3. Scan what you ship. The base image carried 43 fixable CVEs that docker build happily produced.
  4. Pods shouldn't borrow the node's identity; EKS Pod Identity gives each workload its own credentials. The HPA divides by the request: no CPU request, no autoscaling.
  5. Tear down what Terraform doesn't know about first. Kubernetes created the EBS volumes, so terraform destroy alone would have left them behind.
